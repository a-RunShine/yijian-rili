# 0006 日程身份用事件地址，不用 eventIdentifier

- **状态**：已采纳
- **日期**：2026-10-29

## 决策

删除日程时按**事件地址**定位——日历日 + 标题 + 复习备注键 + 目标日历。`createdEventIdentifiers` 降为一次性捷径：先试它，试不着就按地址重查。删除结果返回三态（已删除 / 本来就不在 / 被拒绝并附原因），不再返回 `Bool`。

## 背景

用户反复报告：在主界面逐个删除同一个复习系列时，第一条成功、第二条和第三条弹「删除没有成功」；改去历史记录面板一次删两条却成功，而且时好时坏。

诊断链排除了 UI 与 facade 层（日志显示 `members=1`、`needsSelective=false` 均正确），指向更深处。三个特征只有一种解释能同时满足：

- 逐条失败、批量成功——批量那条路径的成员是当场按标题和日期从日历里现查的
- 时好时坏——取决于日历同步有没有重分配 id
- 删掉第一条之后开始失败——同步在删除后发生

## 理由

`eventIdentifier` 会被日历同步重新分配，Apple 文档明确写了这一点。把它当长期主键，就等于把一个会变的值当身份。

事件地址的四个字段正是我们写进日历的东西，同步改不动它们。代价是查起来比按 id 慢一点（要在某一天的窗口里扫一遍），但删除是低频操作，这点开销无关紧要。

三态返回的理由是信息量：`Bool` 把「已经删掉」「本来就不在」「系统拒绝」压成两个值，调用方拿到 `false` 无法给出能行动的提示。用户看到的「删除没有成功。日程可能正在同步，稍后再试一次」这句话，根子就在这个签名上——它无法说出真实原因，只能让用户重试。

## 替代方案

**删除前强制重置 `EKEventStore`**：曾怀疑是 EventKit 缓存陈旧。但重置是性能与副作用的双输，且无法解释「批量成功」这个反例。

**继续按 id 找，失败时用宽泛扫描兜底**：`resolveEvent` 已经有 ±60 年的扫描，仍在用户机器上失败。说明问题不在兜底范围，而在「找不到就判定失败」这个结论本身。

**把 `createdEventIdentifiers` 改成字典（槽位 → id）**：会改持久化 schema，老数据要迁移。而地址可以从现有字段完整推导，不必动存储。

## 后续影响

- 事件地址必须包含目标日历。丢掉它会让地址退化成「日 + 标题 + 备注」，跨日历误删同名事件。地址匹配到多条时必须拒绝并报告，不能随便挑一条。
- `preferredId` 只是捷径，命中后仍要校验地址对得上；对不上就不采信。
- `createdEventIdentifiers` 与 `reviewDates` 按位置对应。删除时该位置留空串，**不得压缩数组**——压缩会让后面的成员串位，第三次删除就会算错目标。这是同一类缺陷的另一个入口。
- 「本来就不在」不弹提示、不算失败，直接清掉记录。
- 事件的完成与跳过状态挂在系列身份（`series:<条目 UUID>:<序号>`）上，删除时必须一并清掉，否则留下孤儿标记。
